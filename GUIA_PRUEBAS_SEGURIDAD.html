OWASP A04

1. Diseño Inseguro

17 Nov

Prueba 1.1 · Acceso directo a rutas críticas sin autenticación

Verificar que el backend valide JWT y rol (RBAC) en todos los endpoints protegidos, sin depender solo de ocultar vistas en React.

curl.exe -i http://localhost:4000/api/productos
curl.exe -i -X DELETE http://localhost:4000/api/productos/9999
curl.exe -i http://localhost:4000/api/reportes/ventas
✅ Resultado esperado (Seguro)Responde 401 Unauthorized sin token o 403 Forbidden si el rol no es Administrador.
❌ Evidencia si fallaResponde 200 OK o 404 Producto no encontrado sin exigir autenticación.

Prueba 1.2 · Bypass de autenticación multifactor (MFA)

Comprobar que un cliente no pueda saltarse el segundo factor enviando skipMfa: true en el cuerpo JSON del login.

curl.exe -i -X POST http://localhost:4000/api/auth/login `
  -H "Content-Type: application/json" `
  -d '{"email":"admin@admin.com","password":"admin123","skipMfa":true}'
✅ Resultado esperado (Seguro)Ignora skipMfa del body y exige el código OTP (mfaRequired: true).
❌ Evidencia si fallaEmite el token JWT directamente sin pasar por /verify-mfa.

Prueba 1.3 · Protección contra fuerza bruta (Rate Limiting)

Validar que authLimiter (máximo 15 intentos cada 15 min) bloquee peticiones repetitivas.

1..17 | ForEach-Object {
  $code = curl.exe -s -o NUL -w "%{http_code}" -X POST http://localhost:4000/api/auth/login `
    -H "Content-Type: application/json" `
    -d '{"email":"admin@admin.com","password":"wrongpassword"}'
  Write-Output "Intento $_ -> HTTP $code"
}
✅ Resultado esperado (Seguro)A partir del intento 16 el servidor responde 429 Too Many Requests.

Prueba 1.4 · Reglas de negocio (valores negativos en inventario y precios)

Confirmar que el servidor rechaza precios o stock negativos aunque se salten las validaciones HTML del formulario.

curl.exe -i -X POST http://localhost:4000/api/productos `
  -H "Content-Type: application/json" `
  -d '{"nombre":"Prueba Negativo","precio_venta":-500,"stock_actual":-10,"sku":"TEST-NEG-1"}'
✅ Resultado esperado (Seguro)Responde 400 Bad Request rechazando cantidades o precios menores a cero.
OWASP A05

2. Configuración Defectuosa

17 Nov

Prueba 2.1 · Cabeceras de seguridad HTTP (Helmet)

Comprobar que el servidor incluye cabeceras defensivas y oculta X-Powered-By: Express.

curl.exe -I http://localhost:4000/
✅ Resultado esperado (Seguro)No aparece X-Powered-By y sí están presentes X-Content-Type-Options: nosniff, X-Frame-Options / Content-Security-Policy y Referrer-Policy.

Prueba 2.2 · Política de CORS restrictiva

Verificar que orígenes externos no autorizados sean rechazados por CORS.

curl.exe -i -H "Origin: https://sitio-malicioso.com" http://localhost:4000/api/productos
✅ Resultado esperado (Seguro)No devuelve Access-Control-Allow-Origin: * ni refleja el dominio malicioso.
❌ Evidencia si fallaDevuelve Access-Control-Allow-Origin: * permitiendo cualquier sitio web.

Prueba 2.3 · Control de fuga de información en errores y /api/health

Confirmar que las respuestas 404/500 y el endpoint de salud no expongan stack traces ni detalles de base de datos.

curl.exe -i http://localhost:4000/api/ruta-inexistente
curl.exe -i http://localhost:4000/api/health
✅ Resultado esperado (Seguro)404 JSON limpio sin stack trace; /api/health devuelve solo {"status":"ok"} sin dbError ni hasDbUrl.

Prueba 2.4 · Secretos y credenciales por defecto

Inspección de código para verificar que no haya claves fijas ni usuarios con contraseñas débiles predefinidas.

  • Revisar backend/middleware/auth.js: JWT_SECRET debe leerse obligatoriamente de process.env.JWT_SECRET (sin fallback hardcodeado).
  • Revisar backend/index.js: evitar crear admin@admin.com con contraseña admin123 en producción.

Prueba 2.5 · Límite de tamaño de payload JSON

Prevenir ataques de denegación de servicio enviando cuerpos JSON excesivamente grandes.

  • Verificar configuración express.json({ limit: '100kb' }) en backend/index.js y enviar un cuerpo superior al límite.
✅ Resultado esperado (Seguro)El servidor rechaza la solicitud con código 413 Payload Too Large.
OWASP A06

3. Componentes Vulnerables y Desactualizados

17 Nov

Prueba 3.1 y 3.2 · Auditoría de dependencias (Backend y Frontend)

Detectar vulnerabilidades (CVEs) conocidas y paquetes desactualizados en ambos proyectos Node.js.

cd backend
npm audit
npm outdated

cd ..\taller-frontend
npm audit
npm outdated
✅ Resultado esperado (Seguro)0 vulnerabilidades en severidad high y critical (corregidas con npm audit fix o actualización controlada).

Prueba 3.3 · Limpieza de dependencias y validación en CI/CD

Reducir la superficie de ataque eliminando librerías sin uso y automatizando el chequeo en el pipeline.

  • Confirmar la eliminación de dependencias sin uso (ej. mysql2 en backend/package.json al usar PostgreSQL pg).
  • Confirmar que .gitlab-ci.yml o .github/workflows/ci.yml ejecute npm audit --audit-level=high.
OWASP A07

4. Fallas de Identificación y Autenticación

18 Nov

Prueba 4.1 · Política de contraseñas robustas

Confirmar que el registro rechace contraseñas débiles o demasiado cortas.

curl.exe -i -X POST http://localhost:4000/api/auth/register `
  -H "Content-Type: application/json" `
  -d '{"name":"Usuario Prueba","email":"debil@test.com","password":"1234567"}'
✅ Resultado esperado (Seguro)Responde 400 Bad Request exigiendo mínimo 8 caracteres, mayúscula, minúscula, número y símbolo.

Prueba 4.2 · Prevención de enumeración de usuarios

Verificar que las respuestas de error no revelen qué correos existen en la base de datos.

  • Probar POST /api/auth/login con un correo inexistente y luego con un correo válido + contraseña incorrecta.
✅ Resultado esperado (Seguro)Ambos casos devuelven el mismo mensaje genérico (Correo o contraseña incorrectos) y código 401.

Prueba 4.3 · Validación de JWT inválido o ausente

Asegurar que el middleware rechace tokens manipulados, firmados con otra clave o vencidos.

curl.exe -i http://localhost:4000/api/auth/me
curl.exe -i -H "Authorization: Bearer token.invalido.123" http://localhost:4000/api/auth/me
✅ Resultado esperado (Seguro)401 Unauthorized sin token y 403 Forbidden con token alterado o expirado.

Prueba 4.4 · Seguridad del flujo MFA (OTP)

Validar generación segura, expiración, límite de intentos y no exposición del código en la respuesta.

  • Revisar que el OTP se genere con crypto.randomInt(100000, 1000000) y no con Math.random().
  • Verificar que la respuesta de /api/auth/login no incluya otpDev en producción.
  • Probar 5 códigos erróneos consecutivos en /api/auth/verify-mfa y comprobar que la sesión temporal se invalida.
OWASP A08

5. Fallas de Integridad de Software y Datos

Prueba 5.1 · Integridad de dependencias en CI/CD

Garantizar instalaciones deterministas mediante hashes verificados en package-lock.json.

  • Verificar el uso de npm ci (y no npm install) en .gitlab-ci.yml y Dockerfile.

Prueba 5.2 · Manipulación de precios y totales desde el cliente

Confirmar que el backend calcula totales consultando el precio real en PostgreSQL y no confía en el monto enviado por el navegador.

curl.exe -i -X POST http://localhost:4000/api/ventas `
  -H "Content-Type: application/json" `
  -d '{"idUsuarios":1,"metodo_pago":1,"total":1,"items":[{"idProductos":1,"cantidad":5,"precio_unitario":0.01}]}'
✅ Resultado esperado (Seguro)El servidor ignora total: 1 y precio_unitario: 0.01, recalcula con el precio oficial de la tabla Productos o rechaza la petición.

Prueba 5.3 · Prevención de Mass Assignment e integridad de recursos (SRI)

Evitar escalación de privilegios por campos extra en el JSON y scripts externos sin verificación de integridad.

  • Enviar "role":"Administrador" o "idRoles":1 dentro de POST /api/auth/register y verificar que el usuario se cree únicamente como Cliente.
  • Revisar taller-frontend/index.html para confirmar que no existan scripts externos sin atributo integrity (SRI).
OWASP A09

6. Fallas de Registro y Monitoreo de Seguridad

Prueba 6.1 · Registro de eventos de autenticación y accesos denegados

Comprobar que los intentos fallidos de login, MFA y respuestas 401/403 queden almacenados en bitácora.

  • Ejecutar 3 logins fallidos, 1 login exitoso y 1 petición sin token a una ruta protegida.
  • Consultar el archivo de logs o la tabla AuditLogs y verificar campos: fecha/hora, IP, usuario, endpoint y resultado.

Prueba 6.2 · Auditoría de acciones críticas

Garantizar trazabilidad al crear, editar o eliminar productos, usuarios, roles o ventas.

  • Modificar el stock de un producto o cambiar el rol de un usuario y verificar el registro correspondiente en la bitácora.

Prueba 6.3 · Protección de datos sensibles en logs

Asegurar que nunca se escriban secretos en consola ni en archivos de auditoría.

✅ Resultado esperado (Seguro)Tras iniciar sesión y validar MFA, en la consola/logs no aparece el código mfaCode, ninguna contraseña ni el token JWT.
OWASP A10

7. Server-Side Request Forgery (SSRF)

Prueba 7.1 · Bloqueo de red interna y localhost

Verificar que cualquier campo URL procesado por el servidor bloquee direcciones locales o privadas.

URLs de prueba que deben ser rechazadas:
- http://127.0.0.1:4000/api/health
- http://localhost:5432
- http://10.0.0.1/
- http://192.168.1.1/
✅ Resultado esperado (Seguro)Responde 400 Bad Request antes de abrir ninguna conexión saliente.

Prueba 7.2 · Bloqueo de metadatos cloud

Prevenir robo de credenciales en entornos AWS/GCP/Azure mediante la IP link-local de metadatos.

URL de prueba: http://169.254.169.254/latest/meta-data/
✅ Resultado esperado (Seguro)Bloqueada con 400 Bad Request por pertenecer al rango reservado 169.254.0.0/16.

Prueba 7.3 · Protocolos prohibidos y lista blanca de dominios

Confirmar que solo se aceptan URLs https:// hacia dominios explícitamente autorizados.

URLs rechazadas:
- file:///etc/passwd
- ftp://servidor.com/archivo
- https://dominio-no-autorizado.com/imagen.png
✅ Resultado esperado (Seguro)Todas rechazadas con 400 Bad Request; solo pasan dominios en la lista blanca con https://.
